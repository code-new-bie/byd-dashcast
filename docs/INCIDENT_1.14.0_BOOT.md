# 1.14.0 仪表启动故障（2026-10-29）

1.14.0/RWVF仪表包暂停使用。用户确认启动动画播放结束后黑屏，但仍能进入刷机流程。早期提供旧包仅为临时恢复，用户明确要求修复而非以回滚结案；现采用[1.14.1的两LOAD启动修正](PRODUCT_1.14.1.md)，原功能保留。不要卸载或清应用数据，以免丢失正常ADB身份。

## 已定位的不兼容

问题位于新增HMI二进制的装载布局。与上一包比较，只有app.sv变化，内部只改HMI和receiver；原MCU、参考OS、Boot、启动脚本、KZB等保持。动画和恢复流程可用不能单独证明HMI已成功启动。

HMI新增RX LOAD并将程序头表从文件0x34搬到0xac5000。这个布局能被通用ELF解析库读取，却与原参考OS的解释器约定不兼容。原libc.so.3的主程序初始化路径在0x4fbfc读取PT_PHDR.p_offset，0x4eb0c执行AT_PHDR减去该文件偏移，0x4eb18随即读取所得ELF头的e_type。

- 原版：0x08048034 − 0x34 = 0x08048000，为真正ELF头，继续进入程序头解析。
- 1.14.0：0x086f0000 − 0xac5000 = 0x07c2b000，不在已加载段中，随后访问0x07c2b010失败。

已用包中真实解释器字节及两版HMI的PT_LOAD映射执行有界ARM回放，旧版通过/失败版在该读取处失败。此证据复现了明确的启动不兼容，不是运行整套QNX或读取实车core；实际车辆的退出码和回退结果尚未收到。

## 处理与后续约束

公开组件命令明确拒绝生成1.14.0，HMI默认构建也加入实际解释器的地址锚点检查。历史原件、失败包和离线报告保留；旧指令语义测试只能作历史取证，不能再叫作启动合同验收。没有放宽清理、租约、MCU或USB防护来掩盖启动失败。

后续修订必须保留已验证的主ELF地址锚点，并检查原解释器的全部段解析及原生未投屏路径；不能只用通用ELF合法性或Android测试作放行依据。当前优先恢复仪表主界面，再推进新的绘制过滤方案，不把未经确认的新布局交给用户反复刷写。
